BlindsPortal

The operating system for blinds installation companies.

Installation companies that do measure and install work for retailers like Home Depot used to run on paper forms, phone calls, and spreadsheets. BlindsPortal replaces that with one subscription platform. Jobs flow in from the retailer automatically, installers work them from their phones, and the office handles scheduling, payroll, and billing from a desktop app. I designed and built every part of it, and I've run it in production since 2019.

✍️ Built by one person, by hand, before AI. By November 2022, before ChatGPT launched, I had written over 150,000 lines of Go, TypeScript, GraphQL, and Kotlin for it.

The business problem

Two systems that didn't talk to each other

A blinds installation company sits between a big retailer and the customer's living room. The retailer sells the job and sends a purchase order. The installer company sends someone to measure, reports back, waits for the order, schedules the install, collects a signature, and files the completion paperwork. Then it pays its installers.

Every step crossed a system boundary by hand: retyping POs, faxing measure forms, chasing signatures, and reconciling payroll from paper. BlindsPortal's job was to close those gaps without asking a retailer to change anything, and without asking installers who avoid technology to learn much.

The product

One platform, three apps

An installer app for the field, a desktop app for the office, and a Go backend underneath both.

Engineering challenges

What made it hard, and how I solved it

I built BlindsPortal as a complete business system on my own. These are the problems that shaped its design.

1

Integrating with Home Depot and other retailers

Each retailer exposes its work differently, so I defined one Go Plugin interface covering the whole job lifecycle: ingest new purchase orders, react when a job is scheduled, completed, or archived, sync notes both ways, and upload measure forms, waivers, and problem reports back to the retailer. The Home Depot plugin polls for new and canceled POs, manages API tokens, and keeps each company's job list in step with Home Depot's. Blinds.com and Costco plugins followed without any change to the core job model.

Skills: third-party API integration, interface design, data synchronization, extensible architecture

  • Go interfaces
  • API token management
  • Polling ingest
  • Two-way sync
2

An event-driven core that keeps side effects out of the request path

Completing one job can trigger an SMS to the customer, an email, a payroll line, an activity log entry, a document upload to Home Depot, and a notification to admins. I built an in-process event bus with more than 40 event types. Side-effect handlers subscribe to the events they care about and run asynchronously, on a context detached from the HTTP request, so a slow third-party call never blocks the user. The same bus drives scheduled work: start-of-day reminders, payroll and timesheet cycles, billing runs, and checks for stalled jobs.

Skills: backend architecture, concurrency in Go, async processing, job scheduling

  • Goroutines & channels
  • Pub/sub
  • Scheduled jobs
  • GraphQL (gqlgen)
3

A field app that works where the signal doesn't

Installers measure windows in basements and unfinished houses. I built the React Native app to queue every GraphQL mutation locally, apply it to the UI right away, and retry until the server confirms it. Offline operations I wrote handle edits to nested lists such as a job's measures and products, so work done without a connection merges correctly later. I ship fixes to phones over the air through Expo, without waiting on app store review.

Skills: mobile development, offline-first design, optimistic UI, release engineering

  • React Native
  • Apollo Client
  • Offline queue
  • Expo EAS updates
4

Turning paper forms into data, and back into paper

Retailers still expect their own PDF forms: the measure and quote sheet, the customer approval, and the certificate of completion. I built a separate Kotlin and Ktor service that fills the retailer's official fillable PDFs from structured job data, adding pages as a job's measurements grow. Customers sign on the installer's phone or tablet, and the finished document goes straight back to the retailer through the plugin.

Skills: service decomposition, document generation, polyglot systems (Go and Kotlin)

  • Kotlin
  • Ktor
  • PDF form filling
  • E-signatures
5

Running it as a business, solo

I made BlindsPortal multi-tenant: each installation company has its own configuration, integrations, users, and teams. Billing is a per-seat Stripe subscription with automatic retries. Customer messaging goes out through Twilio and Mailgun. I set up GitHub Actions to build and test the Go server and deploy it as a Docker image. It also builds and signs the Electron desktop app for Windows and macOS and pushes installer app updates, so I can ship to four platforms safely on my own.

Skills: SaaS architecture, multi-tenancy, payments, CI/CD, DevOps

  • Stripe
  • Twilio
  • Docker
  • AWS
  • GitHub Actions
  • Electron
