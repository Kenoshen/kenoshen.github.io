HiChore

A family chore chart kids want to open.

Kids tap a chore when it's done, get a burst of confetti, and earn stars to spend in a reward shop their parents stock. I designed, built, and shipped the whole product: the SwiftUI app, the Postgres backend, and the App Store release.

The brief

Simple for a four-year-old, dependable for parents

The kid side had to work for children who can't read yet, so every chore and reward has a picture, big buttons, and a sound. The parent side had to schedule chores by weekday, handle several kids, and lock behind a PIN so the family iPad can stay in Kid View.

The hard part was everything underneath. A real household has a shared iPad on the counter, a phone for each parent, an old iPhone handed down to each kid, and Wi-Fi that drops. Every device needs to show the same star balance. A chore checked off in the car has to count when the phone reconnects, and it can't count twice.

Engineering challenges

What made it hard, and how I solved it

Each of these maps to work I'd do on a backend or platform team.

1

Offline-first sync across every device

Every write goes into a persistent FIFO outbox, keyed by a UUID the client generates. The app updates the screen right away, then sends the queue in order with exponential backoff. If the server rejects a write, the app rolls back that one change and keeps the rest. Because each write has its own ID, sending it again is harmless, so the app never double-counts a chore after a flaky connection. Realtime subscriptions push other devices' changes in. Editable rows resolve conflicts with last-write-wins on updated_at.

Skills: distributed systems, idempotent APIs, eventual consistency, retry and backoff design

  • Outbox pattern
  • Idempotency keys
  • Supabase Realtime
  • LWW
2

Kids get devices, not accounts

Children shouldn't need an email or password. A kid's device signs in anonymously, then pairs to the family with a 6-digit code that expires after 10 minutes. Co-parents join with a single-use invite code. One security-definer function resolves the caller's family from either path. Row-level security checks it on every query, so revoking a device cuts its access immediately.

Skills: authentication and authorization design, multi-tenant security, API design

  • Row-level security
  • Anonymous auth
  • Device pairing
  • bcrypt PIN
3

Business rules the client can't break

The client is never trusted with the numbers. Postgres triggers compute each completion's date in the family's own timezone. They reject chores on unscheduled weekdays and enforce the per-day limit under an advisory lock. Balances move only through triggers, and redeeming a reward locks the kid's row so two devices can't spend the same stars. History is append-only: an undo is a new entry rather than a deletion, so parents can see exactly how a kid reached their total.

Skills: PostgreSQL in depth, data integrity, concurrency control, ledger-style data modeling

  • PL/pgSQL triggers
  • Advisory locks
  • SELECT … FOR UPDATE
  • Append-only ledger
4

Private by design, cheap to run for years

The only data stored about a child is the nickname and avatar a parent picks. Every table carries a family_id in composite foreign keys, so a row can't point at another family's data, and deleting an account cascades cleanly. HiChore is a one-time purchase, so the backend has to stay cheap indefinitely. Nightly pg_cron jobs fold history older than 90 days into monthly totals without changing any balance. A per-family storage budget backs that up. I load-tested the worst case before launch.

Skills: privacy engineering, capacity planning, data lifecycle, cost modeling

  • pg_cron
  • Data compaction
  • Tenant isolation
  • Cascading deletes
5

Tested at the database, automated to the store

The backend has its own pgTAP suite covering access rules, star math, caps, pairing, undo, and the nightly jobs. Each test file runs in a transaction that rolls back. The iOS app has unit tests for its rules and sync engine, plus UI tests. Scripts generate the App Store screenshots, add their captions, and upload builds to TestFlight, so a release is repeatable rather than a day of clicking.

Skills: test strategy, CI/CD and release automation, developer tooling

  • pgTAP
  • XCTest
  • XCUITest
  • TestFlight scripting
