Prycebook

Price books and quotes for service companies.

HVAC, plumbing, and electrical shops often price the same job three different ways, depending on who wrote the quote. Prycebook turns a company's services, parts, and labor into one price book. A tech can build a branded quote in minutes and send it before leaving the driveway, and the customer accepts it from their phone. I designed, built, and launched it by myself in 2026.

Engineering challenges

What made it hard, and how I solved it

Prycebook is a full SaaS business run by one person. These are the problems that shaped its design.

1

A pricing model that matches how trades actually price

Real price books are messy. One item can have Good, Better, and Best tiers, a cost and a price per tier, and units like "per endpoint per month". It can also bundle other items, so a water heater install expands into the heater, the parts, and the labor. Quotes then add discounts, fees, optional lines, and lines hidden from the customer, and they show margin against the company's target. The core domain model comes from pricey, an open-source Go library I wrote for price books and quotes, which Prycebook builds on.

Skills: domain modeling, library design, relational data modeling

  • Go
  • PostgreSQL
  • pgx
  • 66 goose migrations
2

Multi-tenant security, designed in from day one

Every request goes through one middleware chain: recovery, security headers, rate limiting, and CSRF, then authentication, tenant resolution, and a subscription check. Passwords are hashed with Argon2id. Sessions live in Postgres so they can be revoked, and CSRF tokens are bound to the session. Four roles (Owner, Admin, Member, Viewer) gate every action, and every query is scoped to the caller's organization. When I sign in as a customer to help with support, it's recorded in an audit log. The Content Security Policy allows scripts only from the app's own origin.

Skills: application security, auth design, multi-tenancy, RBAC

  • Argon2id
  • CSRF
  • RBAC
  • Strict CSP
  • Audit log
3

Product analytics on ClickHouse

Product events such as sign-ins, quotes sent, and onboarding steps are written to ClickHouse in batches. Materialized views roll each insert up into AggregatingMergeTree tables as it lands. These power the customer-facing Insights page and my own signup, onboarding, and marketing funnel dashboards. Operational telemetry (every HTTP request and SQL query) goes into separate tables with a 30-day TTL. My internal dashboards update over Server-Sent Events only when the data underneath them changes, with no polling.

Skills: analytical databases, data modeling for OLAP, observability, real-time UI

  • ClickHouse
  • Materialized views
  • TTL
  • Server-Sent Events
4

Billing and customer lifecycle as code

Plans are defined in YAML and synced to Stripe by a command that also runs in CI, so prices never drift between environments. Stripe webhooks drive each subscription's state. A Terraform variable turns the beta "Pro free for a year" offer on and off. The app sends the whole lifecycle of email: onboarding, a trial drip held until setup starts, nudges for abandoned onboarding, payment failures, and warnings 30 and 7 days before a free period ends. Every one is scheduled and logged.

Skills: payments integration, event-driven systems, lifecycle automation

  • Stripe
  • Webhooks
  • Scheduled email
  • Feature flags via Terraform
5

Infrastructure locked down end to end

Terraform manages everything on GCP: Cloud Run, Cloud SQL, a ClickHouse VM, Gotenberg for PDFs, and secrets. Every dependency is vendored or pinned. That covers Go modules, front-end assets, Docker images by digest, GitHub Actions by commit SHA, and even the Tailwind binary, so a build needs no network and nothing changes without a commit. Backups come in two layers: Cloud SQL's point-in-time recovery, plus hourly pg_dump snapshots in a bucket outside the database's region. They're written by a service account that can't delete them.

Skills: infrastructure as code, supply-chain security, disaster recovery, CI/CD

  • Terraform
  • Cloud Run
  • Cloud SQL
  • Docker
  • GitHub Actions
